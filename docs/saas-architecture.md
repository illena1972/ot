# План перехода к SaaS

## Цель

Одна установка приложения обслуживает несколько организаций. Данные одной
организации не должны быть доступны другой. Локальная установка продолжает
работать как одна организация без необходимости настраивать домены.

## Хранение данных

Используются два уровня баз данных:

1. Центральная база платформы хранит организации, их статус, адрес доступа и
   параметры подключения к рабочей базе. В ней нет сотрудников, склада,
   выдач или отчетов клиентов.
2. Рабочая база организации хранит все текущие данные приложения, включая
   пользователей, роли, сотрудников, справочники, склад, выдачи, отчеты и
   будущие нормы выдачи.

Для хостинга используется отдельная база MySQL на каждую организацию. Это
обеспечивает изоляцию данных, одновременную работу нескольких пользователей и
независимое резервное копирование. Локальная установка использует тот же MySQL:
на компьютере устанавливается один экземпляр MySQL и создаётся одна рабочая
база локальной организации. Единая СУБД исключает расхождения между локальной
и облачной версиями приложения.

## Организация и вход

Организация определяется до входа пользователя по поддомену, например
`company.example.ru`. Для локального запуска используется организация по
умолчанию. После определения организации Django подключает ее рабочую базу,
а стандартная аутентификация Django проверяет пользователя только в ней.

Центральный администратор платформы создает организацию, рабочую базу и
первого администратора организации. Пользователь организации не получает
доступ к центральной базе и другим организациям.

## Роли

Роли реализуются через стандартные Django Groups внутри рабочей базы
организации.

| Роль | Доступ |
| --- | --- |
| Администратор | Пользователи, настройки организации и все рабочие разделы. |
| Специалист | Сотрудники, справочники, склад, выдача, отчеты и карточки. Без управления пользователями. |
| Просмотр | Отчеты и карточки без создания, изменения или удаления данных. |

В первой версии роли проверяются на сервере для каждого API-запроса. Интерфейс
скрывает недоступные команды, но защита не зависит от интерфейса.

## Этапы внедрения

1. Зафиксировать работающую локальную версию 1.1.
2. Добавить приложение платформы: центральную базу, модель организации и
   безопасный реестр подключений.
3. Добавить маршрутизацию запроса к рабочей базе организации и режим локальной
   установки с MySQL-базой по умолчанию.
4. Включить вход в систему, роли и серверные проверки прав.
5. Реализовать создание организации: база, миграции, группы ролей, первый
   администратор и резервная копия.
6. Проверить изоляцию на двух тестовых организациях.
7. Перенести текущую локальную базу в организацию `Локальная организация` без
   изменения ее данных.
8. После завершения этого этапа добавить нормы выдачи для должностей.

## Правила обновления и резервного копирования

Перед обновлением приложение выполняет миграции для каждой активной рабочей
базы. Резервная копия создается отдельно для центральной базы и для каждой
организации. Ошибка обновления одной организации не должна повреждать данные
других.

## Ограничения первой SaaS-версии

- Одна организация использует один поддомен.
- Сотрудник и пользователь пока не связываются автоматически.
- Подписки, платежи, собственный брендинг и аудит действий не входят в первый
  этап, но модель организации оставляет возможность добавить их позднее.
